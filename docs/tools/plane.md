# Plane 团队协作与项目管理 {#plane}

Plane 把团队要做什么、谁在推进、何时交付和为什么这样做，组织成一套共享的工作记录。读完这篇笔记，你应该能设计一个小项目的工作流，也能分清产品概念、部署方式与许可证。

先记住：工作项是同一份事实；看板、周期、模块和视图帮助你从不同角度理解它。移动一张卡片，不等于真实工作已经通过验收。

核对日期：2026-10-14。界面、版本、套餐与部署要求可能变化，实际使用前应回到相应版本的官方文档。

## 先认识 Plane 的边界 {#plane-overview}

Plane 是项目与工作管理平台，可以围绕工作项规划需求、协作推进、跟踪交付并记录上下文。一个团队可以用它管理固件迭代、产品需求、缺陷处理或跨职能项目。它可以承载敏捷流程，但不要求所有团队照搬同一种 Scrum 仪式。

**先建立共享规则，再配置工具。** 如果“完成”没有验收标准，增加状态、标签和仪表盘不会自动带来可靠交付。Plane 记录人的计划与事实，不自动证明代码正确、测试通过或产品已上线。

- Workspace 工作空间：组织项目与成员的协作边界。
- Project 项目：聚合目标相关的工作项，建立该项目的工作规则。
- Work item 工作项：可追踪的一件事，包含标题、状态、负责人、优先级等属性；描述应补齐背景与验收标准。
- Cycle 周期：把工作放进有起止时间的计划窗口。
- Module 模块：按功能、目标或交付范围组织工作。
- View 视图：保存筛选、布局与排序，观察同一批底层数据。
- Page 页面：承载需求说明、方案和决策等较长上下文。

项目、周期和模块不是必须逐层创建的文件夹。项目包含工作项，周期与模块则给项目里的工作项增加不同维度；视图改变你看到的集合，不创建另一份任务。

## 动手：同一批工作，四种观察范围 {#plane-lab}

下面是一个完全本地的教学模型：虚构的“设备实验室”工作空间有“采集固件”和“网关联调”两个项目。它不连接 Plane，不调用 API，也不会保存、上传或修改任何真实项目。刷新页面或点击“重置演示”都会恢复初始状态。

先切换工作空间、项目、周期、模块，观察可见卡片如何改变；再点击一张卡片，在详情中选择目标状态并应用。所有动作都支持触屏和键盘，不需要拖拽。关闭 JavaScript 后，初始卡片与完整文章仍可阅读。

演示范围固定为：工作空间看全部 6 项；项目看“采集固件”的 4 项；周期看该项目“第 1 轮验证”的 3 项；模块看该项目“采样链路”的 2 项。周期与模块存在交集，但彼此不是父子关系。

## 状态如何表达真实进展 {#plane-states}

Plane 把状态归入五个状态组：Backlog、Unstarted、Started、Completed、Cancelled。项目可以配置具体状态名称，例如官方默认名称中的 Todo、In Progress 和 Done；名称与分组不要混为一谈。

| 状态组 | 这组状态回答什么 | 团队可以如何约定 |
| --- | --- | --- |
| Backlog | 已记录，但还没有进入明确执行计划 | 需求待澄清、缺陷待确认 |
| Unstarted | 已准备开始，实际工作尚未启动 | 验收标准与负责人已经明确 |
| Started | 正在推进中的工作 | 开发中、测试中、评审中 |
| Completed | 达到团队定义的完成条件 | 验收通过，证据与后续说明齐全 |
| Cancelled | 明确不再继续这项工作 | 重复、方案废弃、需求撤回 |

“测试中”可以被配置为 Started 组下的状态；它不是额外的第六种状态组。具体名称与规则取决于项目配置。Cancelled 也不是 Completed：取消的任务应该保留取消原因，不应被当成正常交付成果。

**卡片状态是团队对事实的声明。** 代码合并、自动化测试通过、现场验证完成和正式发布，可能是不同的里程碑。先决定本项目的“完成”究竟要求什么，再让卡片进入 Completed。

在本演示中，可以自由选择五个状态组，便于理解分类。这不代表实际 Plane 实例中的所有用户都能执行任意变更；实际权限、字段与工作流应以当前部署为准。

## 从一个需求走到可验收的交付 {#plane-workflow}

### 先写成能执行的工作项 {#plane-item-template}

把“优化传感器”改写为范围更窄的工作项，例如“校准温度采样并补齐边界值测试”。标题表达动作和对象；描述说明问题、范围、验收标准以及证据。下面的温度点与误差只是教学示例，不是通用产品指标。

```text
标题：校准温度采样
背景：当前读数在低温段偏差较大，需要验证校准方案。
范围：采样换算与校准参数；本项不修改通信协议。
验收：在项目约定的 3 个温度点验证，误差满足约定阈值；
      补齐异常输入与边界值测试，并附测试记录。
负责人：指定推进人；评审人按团队约定参与。
证据：方案说明、变更记录、测试结果与剩余风险。
完成条件：评审及验收通过；后续问题另建工作项。
```

优先级回答“先做哪件事”，负责人回答“谁负责推进”，状态回答“现在到哪一步”，截止日期回答“何时需要结果”。不要用一个字段代替全部管理判断。给工作项命名时保留可验证的目标，避免只写“处理一下”“继续优化”。

### 一轮小迭代的六个动作 {#plane-six-steps}

1. 建立工作空间与项目，先确认成员可见范围和协作方式，不急着做复杂权限设计。
2. 收集需求与缺陷，拆成能说明背景、交付物和验收标准的工作项。
3. 整理 Backlog，去重、澄清范围、明确优先级与推进人；准备好再放入待开始状态。
4. 用 Module 组织功能目标，用 Cycle 选择当前时间窗口内计划推进的工作；容量应基于团队实际情况。
5. 执行期间更新状态，在评论或页面中保留决策与证据。遇到阻碍时记录原因与下一步，避免只把卡片留在“进行中”。
6. 验收通过再完成；复盘未完成项、取消原因与范围变化。需要延续的工作重新评估，不机械地整批挪到下个周期。

做得少而一致，通常比一开始配置大量状态更有效。最小可用约定可以是：每项有明确标题与负责人；开始前说明验收标准；阻碍有下一步；完成时留下结果证据。

## 周期、模块、视图和页面怎么分工 {#plane-dimensions}

### Cycle 关心时间窗口 {#plane-cycles}

周期是有开始和结束日期的时间盒，适合表达“一段时间内计划完成哪些工作”。不要把一个周期永久延长来掩盖未完成工作。周期结束时，查看已完成与未完成的原因，比单看数量更有价值。

同一工作项同一时间只能属于一个周期。即使配置允许并行周期，这条归属约束仍成立。启用并行周期不等于一项任务可以同时计入多个周期。

### Module 关心交付范围 {#plane-modules}

模块按功能、目标或成果组织工作，例如“采样链路”“通信链路”“质量保障”。模块可以有日期，也可以跨越多个周期，因此不能简单理解为“没有日期的周期”。一个工作项可以属于多个模块。

演示中的 SEN-103 同时属于“采样链路”和“质量保障”：前者按功能归类，后者按质量目标归类。它仍是一条工作记录。给多个模块统计求和时，要警惕同一工作项被重复计算。

### View 关心此刻要看什么 {#plane-views}

视图是对已有工作项的筛选、布局和排序。例如“我负责且尚未完成”“当前周期的高优先级工作”“待评审事项”。看板、列表等布局帮助观察同一数据；实际可用布局与功能以版本、版本类型和套餐为准。

一个工作项从视图中消失，可能只是状态或属性不再符合过滤条件，不代表它被删除。追查异常时，先检查筛选条件与项目范围。团队应尽量共享字段含义，避免各自创建一套互不相通的标签。

### Page 关心上下文与决定 {#plane-pages}

把长篇需求说明、设计取舍、会议结论和交付说明放在页面里，并在工作项中引用相应上下文。任务负责追踪动作，页面负责解释为什么。不要只把重要决策留在临时聊天中，也不要把整份方案重复粘贴到每一张卡片。

## Cloud 与自托管：先决定谁负责运维 {#plane-hosting}

部署方式和产品版本类型是两条不同的轴。Cloud 是由服务方运营的服务；self-hosted 自托管是由你或你的团队负责部署运行。自托管又包含 Community Edition 与 Commercial Edition 等版本类型，不能把“自托管”直接等同于“社区开源版”。

### 使用 Cloud 前确认什么 {#plane-cloud}

Cloud 能减少自建服务器、升级和备份设施的直接工作，但仍需评估组织账号管理、数据与附件导出、成员权限、合规要求和相应套餐。数据位置、保留策略、功能与价格都要按实际服务条款及当前方案核实；本文不把它们写成固定承诺。

### 自托管前确认什么 {#plane-self-hosted}

自托管给团队更多部署控制，同时也把可用性、安全补丁、数据保护和故障恢复责任带给团队。官方架构涉及 PostgreSQL 主数据、对象存储附件、Redis 或 Valkey 等缓存服务以及 RabbitMQ 异步任务；组件与连接方式应按选定版本的部署文件确认。

- 先选择 Community 或 Commercial，再选择匹配的安装方式与版本。Docker Compose 文档中的两种安装入口不能互换；不要把 Commercial 安装器称为社区版安装器。
- 明确域名、HTTPS、访问边界、成员管理、邮件发送以及附件存储的实际要求。
- 备份覆盖数据库、附件对象以及恢复需要的配置；加密保存敏感配置，限制备份访问范围。
- 在测试环境演练恢复，而不只确认“备份文件存在”。升级前核对版本路径、迁移说明与回退方案。
- 查看遥测、许可证验证及其他外部连接设置；“自托管”本身不保证没有外联。
- 若选择 Commercial 的官方离线支持，应另行评估 Airgapped 方案与许可要求，不能假设断网后所有商业功能仍可运行。Community Edition 在隔离网络中运行时，也需自行验证镜像获取、依赖服务、遥测配置与离线升级流程；这不等于社区版隔离部署必须购买商业 Airgapped。

本文不提供一键安装命令：安装器、版本、环境要求和 edition 选择相互关联，应直接使用所选版本的官方自托管文档。尤其不要未经审阅就把网络脚本作为日常维护流程执行。

## Community、Commercial 与 AGPL 的边界 {#plane-license}

截至 2026-10-14 核对，官方 makeplane/plane 仓库的 Community Edition 采用 GNU AGPL v3；Commercial Edition 按官方说明属于闭源商业版本，并有相应许可条款和不同权益。免费额度或免费商业层不等于 AGPL 开源版，付费与否也不是判断源码许可的充分条件。

AGPL 允许商业使用，但附有条件。义务取决于你是否修改、分发以及如何向用户提供网络交互等事实。特别是 AGPL 第 13 节：对修改后的程序，如果用户通过网络与其远程交互，应向这些用户提供显著的机会获取相应源码。

**不要把“仅在内网”当作自动豁免，也不要把这条义务解释为“所有业务数据与公司所有源码都必须公开”。** 相应源码的范围、修改和组合方式需要根据实际项目判断；项目记录、附件与代码许可不是同一件事。

选型或二次开发前，至少核对仓库 LICENSE、目标版本、使用的商业功能和对应协议。计划分发修改版、提供托管服务或组合闭源组件时，应由熟悉开源许可的人针对实际方案审查。这里是理解边界的笔记，不代替具体法律判断。

## 与 Beads 放在一起怎么理解 {#plane-beads}

Plane 更适合让人和团队共享计划、状态与上下文；Beads 则更贴近代理与开发工作中的任务记录和依赖关系。两者可以分别服务协作层和执行层，但不是安装后就自动同步的一对产品。

如果同一件事同时出现在两个工具里，先指定哪个记录负责验收状态，另一个保留对应标识与必要摘要。状态不一致时以约定的事实来源为准，避免形成两份长期分叉的待办清单。本页没有配置任何集成、自动同步或双向更新。

进一步阅读：[Beads 任务与依赖笔记](../tools/beads.html)。

## 落地前的检查清单 {#plane-checklist}

- 能说明工作空间、项目、周期、模块和视图各自回答什么问题。
- 项目中的状态组含义一致；完成与取消明确区分。
- 每个计划执行的工作项都有负责人、范围和可核对的验收标准。
- 周期基于真实容量规划；未完成项会重新评估，而不是机械顺延。
- 使用多个模块时知道可能存在交集，不把去重前的总数当成唯一工作量。
- 已确认 Cloud 或自托管的运维责任，并验证备份恢复与访问边界。
- 已按实际版本类型核对功能、许可与外联要求；没有把免费、开源和自托管混为一谈。

复习口诀：项目定边界，工作项记事实；周期管时间，模块管范围，视图换角度，页面留上下文。
