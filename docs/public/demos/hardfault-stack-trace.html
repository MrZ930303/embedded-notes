HardFault 后的 Cortex-M 异常栈回溯分析

从异常入口的 EXC_RETURN 找到硬件压栈所用的 MSP 或 PSP，按帧偏移读取 stacked PC，再用与固件匹配的反汇编核验指令。

按步骤分析交互查看偏移继续看 Cortex-M CPU 寄存器

先确认帧基址

EXC_RETURN → SP

Handler LR 是异常返回标记；被打断上下文的 LR 保存在硬件帧内。M4F 扩展帧的 PC 仍在帧基址 +0x18。

先保留现场，再判断是否能解帧

分析顺序要让每个结论都能回到现场证据。

  1. 冻结现场并记下固件身份。在清除 sticky Fault 状态或继续运行前，记录 HFSR、CFSR 及 MMFAR/BFAR 原值、调试器显示的寄存器和正在运行的构建标识。
  2. 先判断状态和地址是否有效。MMFAR 仅在 CFSR.MMARVALID=1 时、BFAR 仅在 CFSR.BFARVALID=1 时代表本次有效地址；VALID 为 0 时，读到的值可能是旧值。HFSR.FORCED 要继续检查 CFSR；HFSR.VECTTBL 是向量读取相关线索。
  3. 确认硬件帧是否可信。若出现栈压入/弹出错误、栈越界或不可读，停止从该帧解释 PC/LR。不要换用另一条栈凑值。
  4. 由异常入口 EXC_RETURN 选栈和帧类型。先分清 Handler LR 与 stacked LR，再从异常入口选中的 MSP/PSP 帧基址解帧；不要用 Handler CONTROL.SPSEL 或 C handler 序言之后的当前 SP 推断。
  5. 按确定的帧偏移读取核心字段。PC 固定位于帧基址 +0x18；扩展 FP 状态不会把核心字段向后移。
  6. 核对匹配构建中的机器码。只有源码、AXF/ELF、map、符号和反汇编对应实际运行的同一固件，PC 才能映射到有证据的指令。

这篇文章只解释架构帧和证据边界。模拟器不会连接目标板、读取真实 RAM、写入寄存器或判定真实固件根因。

从异常入口 EXC_RETURN 选择栈

对 Armv7-M Cortex-M3/M4 的返回标记，重点看 bit 2、bit 3 和 bit 4。

处理器在异常进入时把被打断上下文的核心寄存器压栈，并将 EXC_RETURN 放入 Handler LR。它不是被打断上下文的普通 LR。基本硬件帧中的 stacked LR 位于帧基址 +0x14。

EXC_RETURN 位选择含义
bit 20：MSP；1：PSP。
bit 30：返回 Handler 模式；1：返回 Thread 模式。
bit 41：基本帧；0：包含 FP 扩展区的扩展帧（需有相应 FPU 扩展）。

Thread 模式可使用 MSP 或 PSP。进入 Handler 后处理器使用 MSP；若被打断的 Thread 选择了 PSP，硬件帧仍压在 PSP 上。因此，Handler 当前 MSP、Handler 的 CONTROL.SPSEL 和异常入口所选栈不能混为一谈。

典型基本帧标记为 0xFFFFFFF1（Handler/MSP）、0xFFFFFFF9（Thread/MSP）和 0xFFFFFFFD（Thread/PSP）；具备 FPU 时可见对应扩展帧标记 0xFFFFFFE1、0xFFFFFFE9、0xFFFFFFED。这些值帮助读位，不代替对真实异常入口上下文的确认。

基本硬件帧的字段偏移

表内偏移均相对异常入口时所选 MSP/PSP 上的硬件帧基址。

字段偏移含义
R0+0x00被打断上下文的 R0。
R1+0x04被打断上下文的 R1。
R2+0x08被打断上下文的 R2。
R3+0x0C被打断上下文的 R3。
R12+0x10被打断上下文的 R12。
stacked LR+0x14被打断上下文保存的 LR，不是 Handler LR 中的 EXC_RETURN。
stacked PC+0x18被打断上下文保存的 PC。地址在帧基址 +0x18。
xPSR+0x1C被打断上下文保存的 xPSR，bit 9 可指示对齐填充。

基本帧为 0x20 字节。硬件帧不包含编译器或 RTOS 另外保存的 R4–R11、S16–S31 等软件上下文；具体软件保存布局要按对应工具链和异常路径独立核对。

Cortex-M4F 扩展帧仍从同一帧基址开始

FPU 是可选实现；bit 4 标出扩展帧时，先按 Armv7-M 帧算法定位 frameptr。

Armv7-M ARM 的 PushStack() / PopStack() 先确定完整帧大小，再以扩展帧起点作为 frameptr。核心帧仍在起点：R0 +0x00、stacked LR +0x14、stacked PC +0x18、xPSR +0x1C。

FP 扩展字段偏移说明
S0+0x20FP 扩展区第一个字。
S1+0x24每个单精度寄存器槽递增 4 字节。
S2–S14+0x28 至 +0x58连续的单精度寄存器槽。
S15+0x5CFP 扩展区最后一个 S 寄存器槽。
FPSCR+0x60浮点状态和控制寄存器槽。
保留字+0x64扩展帧保留槽。

完整 FP 扩展帧为 0x68 字节。不要因 EXC_RETURN bit 4 为 0 而先跳过 0x48 再读 PC：扩展帧的 stacked PC 仍是帧基址 +0x18，不是 SP+0x48。帧基址必须来自硬件异常入口所选栈，而不是 C handler prologue 后已经变化的当前 SP。

对齐填充、可选 FPU 与懒惰保存

帧字段偏移与完整帧后的对齐字是两件事。

CCR.STKALIGN 影响异常入口的 8 字节对齐。若本次压栈产生额外的 4 字节对齐填充，stacked xPSR bit 9 标记该情况。填充位于完整硬件帧之外，不改变 PC 等字段相对帧基址的偏移；恢复异常前 SP 时再根据标记计入这个字。缺少本次 xPSR 或栈证据时，不推测填充是否存在。

FPU 状态还可能使用 lazy stacking：FP 槽被预留，但实际写入推迟。FPCCR.LSPACT 是 bit 0；FPCAR 帮助定位待保存的浮点上下文。预留空间不证明 S0–S15 或 FPSCR 已保存了有效现场值。还需确认目标是否实现 FPU，并核实控制/状态值采集时点。

R4–R11 和 S16–S31 可能在 RTOS 或编译器的软件保存区中，但它们不是这里列出的硬件异常帧字段。

选择一个教学快照

案例 A：精确 BusFault；所给证据支持将 PC 映射到一次无响应的数据访问。

案例 A：精确数据访问错误

Target Cortex-M3
EXC_RETURN FFFFFFF9
MSP 20001000; PSP 20004000
HFSR 40000000; CFSR 00008200; BFAR 60000004
R0 60000000; R1/R2/R3/R12 0
stacked LR 08002019; stacked PC 08001234; xPSR 01000000
AXF at 08001234: LDR r1,[r0,#4]
60000004 has no response

可证到哪一步：FFFFFFF9 选择 Thread/MSP 基本帧。若给出的 MSP 是异常入口帧基址，stacked PC 字段地址为 20001018，值为 08001234。CFSR=00008200 同时置 BFSR.PRECISERR 与 BFARVALID；有效 BFAR 60000004 与 R0 + 4 及同版 AXF 中的 LDR r1,[r0,#4] 相符。题设说该地址无响应，因此这条指令的访问与精确 BusFault 证据吻合。

不能据此断言：数据没有说明 R0 为什么指向该地址，也没有证明更上游的指针或内存破坏原因。不要把原因扩展成“访问地址 0 总会 HardFault”之类的通则。

案例 B：M4F 扩展帧、除零与 lazy FP

Target Cortex-M4F
EXC_RETURN FFFFFFED
MSP 20007000; PSP 20002000
HFSR 40000000; CFSR 02000000
CCR 00000210; FPCCR C0000019; FPCAR 20002020
R0 3C; R1/R2/R3/R12 0
stacked LR 08004101; stacked PC 08003420; xPSR 01000200
AXF at 08003420: UDIV r2,r0,r1; DIV_0_TRP on; R1 0
pre-exception PSP 2000206C

可证到哪一步：FFFFFFED 选择 Thread/PSP 扩展 FP 帧。核心帧没有因 FP 扩展搬移：stacked PC 位于入口 PSP 20002000 + 0x18 = 20002018，其中给定值为 08003420。不要加 0x48 再找 PC。CFSR=02000000 置 UFSR.DIVBYZERO；给定同版 AXF 的整数指令 UDIV r2,r0,r1、R1=0 与 CCR=00000210 中开启的 DIV_0_TRP 相符，HFSR.FORCED 表明该可配置 UsageFault 已升级。xPSR=01000200 的 bit 9 为 1；扩展帧 0x68 字节加 4 字节对齐填充为 0x6C，与给定的异常前 PSP 2000206C 对应。

FPCCR=C0000019 的 LSPACT bit 0 为 1，FPCAR=20002020 是给定的 FP 保存区地址。lazy 状态下预留槽位不等于 S0–S15/FPSCR 已经写入本次有效值。

不能据此断言：快照没有提供 FP 区原始内容，也不能说明为什么 R1 为零。这里是整数 UDIV 除零，不是浮点除零；不要把错误样例中的 SP+0x48 公式套作 stacked PC 偏移。

案例 C：IMPRECISERR 与过期 BFAR

Target Cortex-M3
EXC_RETURN FFFFFFF9; MSP 20003000
HFSR 40000000; CFSR 00000400
BFAR 60000004; BFARVALID 0
stacked PC 08005020; matching AXF at PC: NOP
prior writes: multiple writes
stack-scan candidates 08001001 and 08002005

可证到哪一步：FFFFFFF9 选择 Thread/MSP 基本帧；若该 MSP 是帧基址，PC 字段地址为 20003018。CFSR=00000400 表示 BFSR.IMPRECISERR。这是延迟报告的写错误，给出的 stacked PC 映射到 NOP 并不能定位先前哪一条写指令。

不能据此断言：BFARVALID=0，所以 BFAR=60000004 是未验证的旧值，不能用作本次故障地址。存在多个较早写操作时，08001001 和 08002005 只是栈扫描候选值，不是可靠调用链；需要更早的总线/跟踪证据或受控复现来缩小范围。

案例 D：异常入栈失败，帧不可读

Target Cortex-M3
EXC_RETURN FFFFFFFD
MSP 20007F00; PSP 1FFFFFE0
HFSR 40000000; CFSR 00001000
RAM starts 20000000; task stack 20000000..20000800
PSP timing unspecified; CCR unspecified
exception frame unreadable; stacked PC unknown

可证到哪一步：FFFFFFFD 选择 Thread/PSP，CFSR=00001000 置 BFSR.STKERR。题设明确帧不可读，因此 stacked PC 是未知。给出的 PSP 数值低于 RAM 起始地址，但其采样时点与 CCR 均未提供，不能据此复算对齐填充、精确尝试地址或唯一根因。

拒绝推断：不能改用看起来位于 RAM 的 MSP 凑 PC，不能扫描 RAM 或补零猜帧，也不能虚构 MMFAR/BFAR。现有证据仅够报告所选 PSP 帧不可信和 STKERR；栈耗尽、SP 被破坏、映射或访问问题都需额外证据区分。

读故障状态前先保存原值

地址与位掩码以 Armv7-M/Cortex-M3/M4 状态寄存器布局为例；具体实现仍须核对芯片手册。

CFSR 由 MMFSR、BFSR、UFSR 三段组成。状态位是 sticky 的 W1C 位；先保存原始 HFSR/CFSR 和地址寄存器，再检查有效位。不要先清除现场，也不要在这些教学案例中写故障寄存器。

在 Keil 中匹配实际固件构建

先证实是哪份产物，再解读 PC；调试器给出的调用链只是补充线索。

  1. 固定固件身份。保留目标正在运行固件对应的 AXF/ELF、MAP、源代码版本、Arm Compiler 版本和编译/链接选项；不要拿另一次构建的地址表代替。
  2. 从可信帧取 PC。依据异常入口 EXC_RETURN 与原始选中 MSP/PSP，核实帧边界、stacking fault、xPSR 对齐位以及必要的 FP 状态；C handler 序言之后的当前 SP 不等于入口帧基址。
  3. 逐指令核对。在 µVision 用匹配的 AXF/ELF 和 MAP 打开 Disassembly、Call Stack、Locals，确认 stacked PC 的指令边界、前后指令和源代码映射。优化、内联、尾调用、缺少展开信息会改变可见调用链；不把扫描栈或单个 LR 当完整回溯。
  4. 检查调试器能力。Fault Reports 对话框能否显示取决于当前 debug driver。若该驱动不支持，就按 SCB 地址查看已有寄存器记录；不要因菜单缺失而猜测现场。

不要套用固定的 PC-2、PC-4 或 LR 偏移；应从匹配反汇编和指令边界确认地址含义。

Arm Compiler 6 的 fromelf 可以只读 AXF 并导出反汇编/符号文本，例如：

fromelf --text -c -s --output=firmware.dis.txt firmware.axf

仅对产生该 AXF 的匹配 Arm Compiler 6 安装运行，并核对其确切版本与构建记录；示例读取 firmware.axf，输出清单文件，不执行目标程序。Arm Compiler 5 应使用它自己对应版本的工具和文档，不要将 AC5/AC6 混用，也不要把 AXF 上传到本页模型。

本文不提供通用 naked HardFault handler，不建议在故障处理路径中调用 printf、malloc 或 RTOS API。现场采集需要结合具体工程、编译器 ABI 与设备实现单独设计。

从 stacked PC 核对真实指令

解析字段和认定故障指令是两步不同的工作。

确认帧可信后，再将 stacked PC 映射到与运行固件完全匹配的 AXF/ELF、源码、map、符号和反汇编。优化等级、构建选项或二进制不一致会改变地址对应关系。Keil µVision 的 Disassembly、Call Stack 和 Locals 取决于调试符号、展开信息和调试驱动；调用链视图不能取代硬件帧证据。

不要对 PC 或 LR 固定减 2 或减 4。Thumb 指令有 16 位和 32 位长度；函数指针 bit 0 的状态语义不能直接套用到 stacked PC。按故障类别、异常返回语义、匹配版本反汇编和指令边界核对。RAM 扫描到“像代码地址”的字只能形成候选，不能证明完整调用链。

栈帧不可信时停止推断

保留“不知道”比给出伪精确地址更有用。

STKERR、UNSTKERR、栈越界、内存不可读、lazy FP 保存错误或明显损坏，都可能使硬件帧不可用。将字段标为未知/不可信，检查栈边界、栈指针破坏、访问权限和芯片内存映射；不要切换到另一条栈凑 PC，不要补零或扫描 RAM 拼出调用链。

报告应分清直接可证字段、仅支持一种解释的线索、以及现有现场无法确认的结论。HardFault 入口本身不提供唯一根因。
