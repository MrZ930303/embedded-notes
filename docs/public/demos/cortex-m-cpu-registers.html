Cortex-M · Armv7-M / M4 教学模型

Cortex-M CPU 核心寄存器

从 R0 到 PC，再到状态、屏蔽和控制寄存器。先分清硬件寄存器的作用，再看函数调用、异常进入和栈选择怎样使用它们。

点选寄存器试算异常屏蔽查看 MSP / PSP继续：HardFault 栈回溯

先记住三个别名

R13 = SP
R14 = LR
R15 = PC

SP、LR、PC 不是额外的一组寄存器，而是通用寄存器编号中的特殊用途别名。

一张图看懂寄存器组

Armv7-M 的 Cortex-M3/M4 有 R0–R15 的 32 位核心寄存器视图。R0–R12 可作通用数据寄存器；R13、R14、R15 分别承担 SP、LR、PC 的架构角色。处理器架构定义这些寄存器的硬件语义；AAPCS32 另行规定函数调用时软件应怎样保存和传递值。

本文以 Armv7-M Cortex-M3/M4 为主。以下互动使用明示的 Cortex-M4 教学配置；它用于解释概念，不验证任何具体芯片、固件或 NVIC 配置。

不要混淆两层约定：“R0 是函数参数寄存器”来自过程调用约定；“R13 是栈指针”是处理器寄存器角色。编译器遵循 ABI，但硬件不会因 C 函数声明而替你决定每个通用寄存器的用途。

寄存器核心语义AAPCS32 调用约定
R0–R3通用寄存器前四个整数参数通常经 R0–R3 传递；R0/R1 也可承载返回值。调用者保存。
R4–R8、R10–R11通用寄存器被调用者保存：函数若修改它们，返回前须恢复原值。
R9通用寄存器平台寄存器或被调用者保存，取决于平台和 PCS 变体；不能一概说成普通 scratch。
R12 / IP通用寄存器 / 过程间临时寄存器调用者保存的临时寄存器；链接器 veneer 也可能使用它。
R13 / SP当前栈指针别名指向当前活动栈；Cortex-M 有 MSP、PSP 两个栈指针。
R14 / LR链接寄存器别名普通子程序返回链接；异常入口时可能装入 EXC_RETURN。
R15 / PC程序计数器别名控制流寄存器，不是普通参数寄存器。

调用规则见 AAPCS32 §6.1.1；硬件语义见 Arm Cortex-M4 Devices Generic User Guide，§2.1.3 与 ST PM0214 Rev 10，§2.1.3。

点选寄存器：它现在代表什么？

选择 R0–R15 或特殊寄存器。这里强调 Cortex-M4 的架构角色；是否有可选扩展仍要看芯片实现。

R0

通用寄存器。AAPCS32 将 R0–R3 用作前四个整数参数寄存器和调用者保存的临时寄存器；R0 也承载常见的单字返回值。

通用寄存器调用者保存

R13 / SP、R14 / LR、R15 / PC

R13 / SP：MSP 与 PSP

R13 是当前 SP 的别名。Cortex-M 具备主栈指针 MSP 和进程栈指针 PSP；任一时刻由当前执行上下文使用其中一个。CONTROL.SPSEL 只选择 Thread mode 使用哪个栈：0 为 MSP，1 为 PSP。Handler mode 始终使用 MSP。

异常从 Thread 进入 Handler 时，处理器先把自动异常帧压入异常发生前正在使用的 Thread 栈。若 Thread 用 PSP，帧先写到 PSP；随后 Handler 在 MSP 上运行。不能只看 Handler 中的 SP 就认为它指向那份帧。

R14 / LR：普通返回链接与 EXC_RETURN

普通函数调用中，LR 保存返回链接。异常入口会把一个特殊的 EXC_RETURN 标记放进 LR，用来描述异常返回时的目标模式、栈和帧类型；它不是普通代码地址。刚进入异常时常见基本帧示例为 0xFFFFFFF9（返回 Thread / MSP）或 0xFFFFFFFD（返回 Thread / PSP）；嵌套异常返回 Handler 的示例为 0xFFFFFFF1。这些示例限定在 Armv7-M 的基本帧场景；带浮点扩展帧时 EXC_RETURN 还有其他状态位。C Handler 再调用函数后，活跃 LR 也可能被普通调用覆盖，编译器序言通常会保存需要保留的值。

R15 / PC：当前执行位置和 Thumb

在 Cortex-M4 常见的读 PC 情境中，读出的值通常是当前指令地址加 4；某些 PC-relative 计算还会先按字对齐，所以不是所有指令都能用一个固定偏移反推。Cortex-M 执行 Thumb 指令；对 BX/BLX 或会把目标写入 PC 的相关形式，目标最低位为 1 表示 Thumb 状态，分支时该状态位不作为实际取指地址的一部分。不要把这个最低位当作普通偶/奇字节地址来解释。

寄存器别名、栈选择与 EXC_RETURN 见 ST PM0214 Rev 10，§2.1.3、§2.3.5 和 Arm Cortex-M4 Generic User Guide，§2.1.3、§2.3。

xPSR：APSR、IPSR、EPSR 的组合视图

xPSR 是程序状态字的组合视图，由 APSR、IPSR、EPSR 的不重叠字段组成。调试异常帧时，栈中保存的 xPSR 还记录异常上下文；不要把三个视图当成三份互不相关的全宽寄存器。

视图主要内容阅读注意
APSRN、Z、C、V 条件标志；Q 饱和标志；DSP 扩展可带 GE 字段。GE 等字段取决于已实现的指令扩展；M4 常有 DSP 扩展，但不要据此概括每个 Cortex-M。
IPSR当前异常号；0 表示 Thread mode。外部 IRQn 的异常号从 16 + IRQn 开始。通过普通软件状态寄存器接口读取；不能用 MSR 写入 IPSR。
EPSR执行状态，例如 Thumb 状态，以及实现中存在的 IT/ICI 状态位。不是通用可写寄存器；普通 MRS 读取 EPSR 视图时其位读为 0，MSR 对 EPSR 字段的写入会被忽略。调试时优先读取 xPSR 或异常栈帧。

寄存器访问见 CMSIS-Core 6 Core Register Access；字段与栈帧见 ST PM0214 Rev 10，§2.1.3、§2.3.5。

PRIMASK、FAULTMASK、BASEPRI：屏蔽激活，不是清 Pending

寄存器Armv7-M / Cortex-M3/M4 中置位后的作用重要例外
PRIMASK = 1阻止所有可配置优先级异常的激活。NMI 和 HardFault 不受 PRIMASK 屏蔽。
FAULTMASK = 1阻止除 NMI 外所有异常激活，包括 HardFault。异常返回时通常自动清除；从 NMI 返回时不按此规则自动清除。
BASEPRI = 0关闭 BASEPRI 阈值屏蔽。不代表解除 PRIMASK 或 FAULTMASK。
BASEPRI 非零阻止优先级数值等于或低于（数值更大、更不紧急）阈值的可配置异常激活。高于阈值的可配置异常仍可激活；NMI 和固定优先级 HardFault 不由 BASEPRI 屏蔽。

这些寄存器控制“是否可以激活异常”，不会清除 NVIC 的 Pending 位，也不会结束已经在执行的 Handler。Pending 请求可能继续等待，直到它变得可激活或软件/外设按相应机制清除；已经 Active 的处理程序会继续运行。写入屏蔽状态需遵守特权限制。FAULTMASK 不能在 NMI 或 HardFault 的优先级下被有效置位。

同步故障、SVC、优先级仲裁、故障升级和 Lockup 有各自的异常规则；本交互把普通可配置优先级 IRQ 与固定优先级 NMI/HardFault 分开展示，不把某个 C 操作笼统说成必然触发 HardFault。

来源：ST PM0214 Rev 10，§2.1.3、§2.3.2、§4.3.5–4.3.7；CMSIS-Core 6。

BASEPRI 的编码：4 个实现位的示例

NVIC 优先级寄存器是左对齐的字节；具体芯片实现多少个高位由实现决定，未实现的低位读为 0、写入被忽略。数值越小，优先级越高；0 是最高的可配置优先级。BASEPRI 使用相同的编码方向，0 是“禁用 BASEPRI 阈值”，不是“屏蔽所有优先级”。

CONTROL：Thread 特权级、栈选择和浮点上下文

在 Cortex-M4 中，CONTROL.nPRIV 描述 Thread mode 的特权状态；CONTROL.SPSEL 选择 Thread mode 使用 MSP 还是 PSP。Handler mode 始终特权运行并使用 MSP。若实现了 FPU，CONTROL.FPCA 表示当前浮点上下文状态；它不是开启 FPU 的开关。

位含义边界
nPRIV (bit 0)0：Thread 特权；1：Thread 非特权。Handler 始终特权。非特权 Thread 不能仅靠写 CONTROL 把自己升回特权；需由特权异常处理流程或复位改变。
SPSEL (bit 1)0：Thread 使用 MSP；1：Thread 使用 PSP。只决定 Thread 栈。Handler 当前栈始终是 MSP。
FPCA (bit 2)FPU 实现中表示浮点上下文活动状态。仅对带 FPU 的实现有意义，可影响异常浮点状态保存/延迟压栈；不启用 FPU。

特权代码更改 CONTROL 后应紧接着执行 ISB，让后续指令按新的特权状态和 Thread 栈选择继续执行。常见次序为 MSR CONTROL, Rn; ISB。非特权 Thread 不能通过写 CONTROL 清除 nPRIV 来提升权限。

不要把所有 Cortex-M 当成同一套寄存器

内核架构轮廓与本文相关的差异
Cortex-M0Armv6-M有 PRIMASK；没有 BASEPRI、FAULTMASK；CONTROL.nPRIV 不支持（bit 0 保留）。
Cortex-M0+Armv6-M有 PRIMASK；没有 BASEPRI、FAULTMASK；特权/非特权支持取决于实现，不能假定每个 M0+ 都有 nPRIV。
Cortex-M23Armv8-M Baseline有 PRIMASK；没有 BASEPRI、FAULTMASK。不能照搬 M3/M4 的屏蔽控制。
Cortex-M3 / M4Armv7-M / Armv7E-M本文主要模型：PRIMASK、FAULTMASK、BASEPRI；M4 的 FPU 仍为可选。
Cortex-M7Armv7E-M具备 Mainline 屏蔽寄存器模型；FPU 配置可选，实际功能按实现核对。
Cortex-M33Armv8-M Mainline有 BASEPRI、FAULTMASK；安全扩展与 FPU 等可选配置会带来额外状态差异。

M0/M0+ 差异见 Arm Cortex-M0 Generic User Guide、Arm Cortex-M0+ Generic User Guide；M23/M33 的 Baseline/Mainline 区别见 Armv8-M 架构与程序员模型指南。Armv7-M 与 Armv7E-M 的扩展边界见 Armv7-M Architecture Reference Manual。

怎样把寄存器知识用于调试

  1. 先确认目标芯片具体 Cortex-M 内核、架构版本和可选 FPU/安全扩展。
  2. 按芯片参考手册、设备头文件中的 __NVIC_PRIO_BITS 与优先级分组核对实际 NVIC 配置。
  3. 在调试器中区分当前模式、活动 SP、入口时的 EXC_RETURN 与保存到异常帧中的 LR；不要把普通子程序 LR 当成异常返回标记。
  4. 用编译器对应 ABI/AAPCS 解释调用现场的 R0–R12 保存规则，而不是只凭寄存器编号猜 C 变量。

交互器固定采用 4 个已实现优先级位的 Cortex-M4 教学模型。它不会读取目标设备，也不能验证启动代码、NVIC 分组、库宏或固件屏蔽效果；请把本机芯片手册、CMSIS 设备头文件和实机调试结果作为配置依据。
